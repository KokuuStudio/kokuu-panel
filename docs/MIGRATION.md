# 从 kokuu-credit-admin + exchange-bridge 迁移

目标：**不停机、不丢账、可回滚。**

现有部署是「皮肤站 / 管理台 → 中间件 → Redis 队列 → exchange-bridge → Vault」。
新平台把中间件与管理台合并，并把执行通道从队列换成能带回执的 Agent RPC。

---

## 1. 什么变了，什么没变

| | 变了吗 | 说明 |
|---|---|---|
| Blessing Skin 皮肤站 | **没变** | 它调的还是 `POST /api/game/convert` 那套 HTTP 接口 |
| Redis 兑换队列 | **没变** | `bs:exchange:queue` / `bs:exchange:result` 的 key 与消息格式保持不变 |
| 账本数据 | **没变** | 迁移脚本按原表逐行搬，`event_id` 唯一索引一起搬（幂等的历史必须保留） |
| 管理台地址 | **变了** | 端口与路径可能不同，需要改书签与任何硬编码的调用方 |
| `X-Admin-Token` 鉴权 | **变了** | 换成多账号 + 会话 Cookie + CSRF。有脚本在调 API 的话必须改 |
| 金币回流 | **变了** | 从「插件扫余额 + 队列上报」改成 Agent 上报事件，比例仍然以插件侧为准 |

**换掉 `X-Admin-Token` 是这次迁移里唯一会打断自动化脚本的改动。**
如果你的部署里有定时脚本在调 `/api/*`，先在平台里建一个专用账号，
把它的会话 Cookie 固化到脚本里 —— 或者先保留旧中间件只读运行一段时间。

---

## 2. 迁移前

1. **备份。** 旧仓库的 `bash scripts/backup.sh` 会生成
   `data.tar.gz` + `db.sql` + `redis.tar.gz`。**Redis 必须备份** ——
   回流事件在队列里等着被消费，队列丢了等于「玩家金币已扣、积分没入账」。
2. 记下当前的兑换配置（`ratio` / `min_coin` / 各项限额）。
   迁移后要填进平台的「经济 → 配置」页。
3. 确认新平台能连上同一个 Redis。

---

## 3. 迁移账本

> 🛑 **不要按本节做。** 本节写于「平台自建账本」那个错误前提之下。
>
> 正确的做法是**不迁移账本**：唯一账本（Blessing Skin 的 `users.score` +
> `credit_ledger`）留在原处，平台只做它的操作界面。
> 见 [`ECOSYSTEM.md`](ECOSYSTEM.md)。
>
> 下面保留原文，仅为记录「当时是怎么想的」，其中字段映射与
> 「跳过而不是覆盖」的纪律仍然有参考价值。

> ⚠️ **本节目前是操作说明，不是现成脚本。** 迁移工具（`migrate-ledger`）
> 依赖旧仓库的具体表结构，而 `kokuu-credit-admin` 的账本有三套实现
> （`local-ledger.js` / `ledger.js` / `skin-ledger.js`），字段并不完全一致。
> 写这个脚本之前必须先确认你用的是哪一套。下面给出映射关系与做法。

### 字段映射

| 旧（`kokuu-credit-admin`） | 新（平台） | 备注 |
|---|---|---|
| 用户标识（UID / 皮肤站 `users.id`） | `economy_accounts.uuid` | **需要一次 UID → MC UUID 的转换**，见下 |
| `score` / 余额 | `economy_accounts.balance` | 直接搬 |
| 流水 `event_id` | `economy_ledger.event_id` | **必须原样保留** |
| 流水 `delta` / `note` / `source` | 同名字段 | 直接搬 |
| 流水时间 | `economy_ledger.created_at` | 毫秒时间戳 |

**最容易踩的坑是身份锚点不同。** 旧系统的账本键是皮肤站的
**用户 UID**（整数），新平台一律用 **MC UUID**（字符串）——
这是本平台「UUID 作身份锚点」原则的直接后果：玩家名可改可重名，
皮肤站 UID 与游戏内身份之间没有天然映射。

所以迁移的第一步是**建立 UID ↔ UUID 映射**：

1. 从皮肤站导出 `users` 表（`uid`、`username`、`uuid` 若有）
2. 若皮肤站存了 `uuid` 字段，直接用
3. 否则用玩家名去平台的 `player_names` 表匹配（平台侧玩家的名字历史
   会在他们上线后自动积累，所以**先让服务器跑一段时间再迁移账本**更稳）
4. 匹配不上的行**不要丢**：导出成一份清单人工处理，
   或者挂到一个专门的「待认领」账户上

### 做法

1. 从旧库导出余额与流水：
   ```bash
   mysqldump -u root -p <旧库> <余额表> <流水表> > /tmp/ledger.sql
   ```
   或从皮肤站导出（skin 模式下账本就在 `users.score`，见下）。
2. 建立 UID → UUID 映射（上一步）。
3. 按上表映射后，用平台的存储层逐行写入。**幂等靠
   `economy_ledger.event_id` 的唯一索引**：重复的行插入会失败，
   跳过并计数，不要覆盖。

   > 跳过而不是覆盖，这一条很重要：旧库里的 `event_id` 是幂等的依据，
   > 覆盖会让「同一笔交易被记两次」变成无法检测的历史脏数据。

4. 迁移完成后核对：平台总余额 + 跳过行数应当能对上旧库总和。

### skin 模式（账本在 Blessing Skin 的 `users.score`）

积分本体是皮肤站的 `users.score`，**不需要迁移**。平台以只读方式
读它、以事务方式写它（与旧中间件的 `skin-ledger.js` 同样的做法）。
唯一要做的是把皮肤站的库连接信息填进平台配置。

## 4. 迁移执行通道

这是**唯一需要停机窗口**的一步，但通常只有几分钟。

```
旧：皮肤站 → 中间件 → Redis 队列 → exchange-bridge（旧插件）
新：皮肤站 → 平台   → Redis 队列 → KokuuAgent（新插件）★ 队列路径仍然可用
    管理台 → 平台   → Agent RPC  → KokuuAgent        ★ 新增直连路径
```

**两种做法，按你的风险偏好选：**

### 做法 A：先换插件，队列 key 不变（推荐，几乎无停机）

`KokuuAgent` 同时实现了队列消费与 RPC 两条入口，共用同一个执行器核心。
所以可以：

1. 先把 `KokuuAgent` 装上去，`config.yml` 里队列 key 填**与旧插件相同**的值
2. 停掉旧插件、启用 `KokuuAgent`
3. 皮肤站与中间件完全不用改

队列里积压的消息会被新插件接管消费。

### 做法 B：两边并行（保守，但要注意重复执行）

旧插件与新插件**不能同时**消费同一个队列 —— `BRPOP` 是「取走即消失」，
两个消费者会各拿一半，最终表现为「有些订单发了、有些没发」。

要并行就必须用不同的队列 key，而皮肤站只能配一个。所以**做法 B 实际上
做不到**，除非在皮肤站侧做双写。建议直接用做法 A。

### 关于回流

旧插件的 `reflow` 是「扫描余额 + 比例抽成 + 队列上报」。
`KokuuAgent` 保留了这个逻辑，比例仍然**以插件侧为准**
（扣币发生在插件这里，算式必须在同一处完成）。

迁移时确认两边的比例一致：插件 `reflow.ratio` ↔ 平台「兑换比例」。
不一致时平台会打「比例漂移」告警，但**检测到照样入账** ——
玩家的金币已经扣了，不入账等于让玩家白亏。

## 5. 迁移后自检

```bash
# 不变量
pnpm test

# 端到端
pnpm verify --password <管理员口令>
```

再手工确认这四件事：

1. **账本对得上**：平台「经济 → 概览」的总余额 ≈ 旧库的总和
   （被跳过的重复行会让两者有一点点差，差额应当能对上日志里的跳过计数）
2. **队列在消费**：`/kp status` 里「待发放」不持续增长
3. **回流在跑**：平台的「回流统计」有计数，`drift` 为 0
4. **封禁生效**：在平台上封一个小号，立刻在游戏里试登录 —— 应当被拒

第 4 条要特别验：**旧的 exchange-bridge 不管封禁**，所以这是新能力，
没有可对照的旧行为。

---

## 6. 回滚

平台不修改旧仓库的任何数据，所以回滚是**换回插件**：

1. 停掉 `KokuuAgent`，装回 `exchange-bridge`
2. 中间件与管理台启动回旧版本
3. 队列 key 不需要改（两边用的是同一套）

**回滚会丢掉的是**：迁移后在平台上做的封禁、LuckPerms 变更、审计记录。
这些在旧系统里没有对应位置，所以**回滚前先导出留档**：

```bash
# 当前没有现成的导出脚本；直接查库即可（SQLite）
sqlite3 data/kokuu.sqlite ".mode json" \
  "SELECT * FROM audit_log ORDER BY ts;" > /tmp/audit-before-rollback.json
```

审计表结构见 [ARCHITECTURE.md §6.2](ARCHITECTURE.md)。

> 经济数据不会丢 —— 它的权威始终在数据库 / 皮肤站，不在平台内存里。

## 7. 常见问题

**皮肤站订单卡在「发放中」**
队列 key 或 Redis 前缀不一致。旧仓库的 README 里记过一个真实事故：
Laravel 的 Redis 门面会在**扩展层**加前缀
（`blessing_skin_database_`），而裸 Jedis 不加。自查：

```bash
redis-cli --scan --pattern '*exchange*'
# 结果带 blessing_skin_database_ 前缀 → 皮肤站侧没清前缀，必坏
```

**`/kp status` 显示「未找到经济插件的经济类」**
Vault 没绑定。检查经济插件是否经 Vault 注册；只有不实现 Vault 的后端
才需要在 `config.yml` 的 `economy.class-names` 里填全限定类名。

**平台显示「0 人在线」但服务器里有人**
正常情况下握手时会自动对齐在线玩家（`reconcileOnlinePlayers`）。
如果仍然为 0，检查 Agent 是否声明了 `players` 能力，
以及日志里有没有「对齐节点 X 的在线玩家失败」。

**「待回传积压」一直涨**
这是旧仓库的既有设计（皮肤站侧没有常驻 worker，结果靠玩家访问页面时消费），
不是迁移引入的问题。介意的话在皮肤站加个 cron 调 `drain_results()`。
